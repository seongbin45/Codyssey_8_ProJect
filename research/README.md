# 관련 연구 (Related Work)

> 이 문서는 최종 `README.md`의 "관련 연구" 섹션 초안이다. "내 데이터를 아는 AI 비서"의 핵심 설계—
> `GET /api/data/summary`로 시계열 데이터를 미리 집계한 뒤, 그 요약 텍스트를 통째로 LLM의 system
> prompt에 끼워 넣고(`services/chat_service.py`), 검색(retrieval)도 도구 호출(tool call)도 없이
> 단발성으로 답변을 받는 구조—가 "LLM이 데이터 분석을 중계할 때" 존재하는 훨씬 넓은 연구 스펙트럼
> 어디에 위치하는지를, 5개 하위 분야를 넓게(합계 약 650편 이상의 논문·시스템·벤치마크 카탈로그화) +
> 깊게(핵심 논문 40편 심층 분석) 조사해서 정리했다.

## 1. Text-to-SQL / 자연어 기반 데이터베이스 질의 인터페이스 (NLIDB)

"자연어 질문 → 구조화 데이터 접근"이라는 문제를 반세기 가까이 다뤄온, 가장 오래되고 방대한 연구 흐름이다.
1970년대 규칙 기반 시스템(LUNAR)부터, 2019년 스키마를 그래프로 인코딩해 파인튜닝하는 RAT-SQL, 2023년
이후 in-context learning만으로 SQL을 생성하는 DIN-SQL·DAIL-SQL, 실제 DB 값과 외부 지식을 함께
주입하는 BIRD, 대규모 DB에서 관련 스키마만 검색해오는 CHESS, 그리고 다중 턴 에이전틱 워크플로우로
진화한 Spider 2.0까지 스펙트럼이 넓다.

**우리 프로젝트와의 비교**: 우리는 SQL(또는 그에 준하는 구조화 질의)을 전혀 생성하지 않는다—질의 자체가
없고, 이미 계산된 요약 하나만 프롬프트에 박아 넣는다. 이는 이 분야 전체를 통틀어 가장 단순한 극단에
해당한다. BIRD가 "DB 값 + 외부지식 evidence를 텍스트로 프롬프트에 주입"하는 방식은 사실 우리 접근과
철학적으로 가장 가깝다.

**이 분야에서 배울 점**: (1) LEVER처럼 실행 결과를 검증기로 되먹이는 피드백 루프, (2) CHESS처럼 데이터가
많아질 때 관련 부분만 검색해오는 방식, (3) DIN-SQL의 자체 재검토(self-correction) 단계.

이 분야가 반복적으로 지적하는 실패 원인(스키마 링킹 오류가 실패의 60%+ 원인, 복잡한 조인 실패, 강건성
부족)은, 우리가 향후 "질의를 좀 더 구조화"하는 방향으로 확장할 때 미리 대비해야 할 함정이기도 하다.

## 2. RAG(Retrieval-Augmented Generation) 및 구조화 데이터 컨텍스트 주입

RAG의 원조(Lewis et al. 2020, REALM, RETRO)부터, 그래프/전역 요약 기반 GraphRAG, 표(table) 전용 RAG,
시계열+LLM 결합 연구(Time-LLM), 그리고 "Long-context 모델이 충분히 커지면 RAG가 필요 없어지는가"라는
현재진행형 논쟁까지 다루는 분야다.

**우리 프로젝트와의 비교**: 우리 시스템에는 검색(retrieval) 단계 자체가 없다—벡터 임베딩도, 유사도
검색도, 청크 분할도 없이 규칙 기반으로 전체 요약을 매번 통째로 주입한다("rule-based full-context
injection"). 이는 RAG 스펙트럼 밖, 오히려 "요약 기반 압축 + long-context" 계열에 더 가깝다. 대화가
길어지면 이전 메시지 전체를 다시 보내는 방식도 같은 철학의 연장이다.

**이 분야에서 배울 점**: (1) 데이터가 지금의 120건보다 훨씬 많아지면 질의에 따라 관련 구간만 뽑아오는
semantic search 도입, (2) 대화가 길어질 때 전체 재전송 대신 대화 자체를 요약해서 압축, (3) 답변에 근거
출처를 추적/인용하는 grounding 장치 추가.

## 3. LLM 에이전트 + 도구/코드 호출(Tool/Function Calling) 기반 데이터 분석

ReAct의 plan→act→observe 루프를 데이터 분석에 적용한 Data-Copilot, TaskWeaver, Data Interpreter,
그리고 코드를 직접 실행해 관찰 결과를 다시 컨텍스트에 넣는 CodeAct 같은 계열이다. 과제의 보너스 항목
(Function Calling)이 정확히 이 분야에 해당한다.

**우리 프로젝트와의 비교**: 우리 시스템은 계획(plan)도, 도구 호출(tool call)도, 관찰(observation)
피드백 루프도 없는 "정적 컨텍스트 주입형" 단발성 구조다. LLM은 미리 계산된 텍스트를 읽고 답할 뿐, 스스로
무엇을 더 조회할지 결정할 수 없다.

**Function Calling 확장 시 구체적 제안** (심층 분석에서 도출):
1. `get_summary` 하나를 여러 개의 호출 가능한 도구(기간별 조회, 특정 지표 조회 등)로 쪼개기
2. 관찰 피드백 루프를 넣되 `max_tool_calls` 상한을 둬서 무한 루프 방지
3. InfiAgent-DABench의 교훈대로 도구 응답 포맷을 엄격한 스키마로 강제해 파싱 오류 방지
4. TaskWeaver/LIDA처럼 planning 단계와 실행 단계를 분리

이 분야의 대표적 실패 모드(무한 루프, 잘못된 도구 선택, 코드 실행 오류, 비용/지연시간 증가)는 우리가
Function Calling을 실제로 붙일 때 설계 단계에서부터 고려해야 한다.

## 4. 대화형 BI(Conversational BI) / 자연어 기반 데이터 시각화

DataTone·FlowSense·Voyager 같은 고전 규칙/통계 기반 시스템에서, Chat2VIS·LIDA·Data Formulator·
DracoGPT처럼 LLM이 파이프라인 여러 단계(의도 파싱, 차트 타입 선택, 데이터 변환)에 깊이 개입하는 현재
세대까지를 다룬다.

**우리 프로젝트와의 비교**: 우리는 텍스트 요약만 채팅으로 제공할 뿐 시각화가 전혀 없다. VisEval 벤치마크
기준 GPT-4조차 75.27%의 정확도(CodeLlama-7B는 28.17%)에 그친다는 사실은, 시각화 자동 생성이 결코
쉬운 문제가 아님을 보여준다.

**시각화 1개 추가 시 구체적 제안** (바닐라 JS 제약 고려):
1. LLM의 역할을 "필드→차트 타입 매핑 결정"으로 좁히고, 실제 렌더링은 결정론적 라이브러리/캔버스에 맡기기
2. LIDA의 Goal Explorer처럼 차트 옆에 자동 하이라이트 캡션 붙이기
3. DataTone처럼 모호한 질의에 대해 "이렇게 해석했어요" 확인 칩(chip) 노출
4. 채팅 응답에 인라인 스파크라인 데이터를 함께 실어 최소한의 개선 루프 지원

## 5. 평가·벤치마크·신뢰성 (Evaluation & Reliability)

DS-1000·InfiAgent-DABench·TableBench 같은 실행/정답 기반 벤치마크, RAGAS·G-Eval 같은 자동 평가
프레임워크, FActScore·SelfCheckGPT 같은 hallucination 탐지 기법, 그리고 FAITH처럼 금융 수치 추론이
복잡도에 따라 정확도가 지수적으로 붕괴하는 것을 보여주는 최신 벤치마크까지 다룬다.

**우리 프로젝트와의 비교**: 우리 시스템은 자동화된 평가가 전혀 없다—사람이 몇 번 채팅해보고 답변이
그럴듯한지 눈으로 확인하는 수준이다. 그 와중에 실제로 겪은 버그(gpt-5-mini가 추론 토큰으로 `max_tokens`
예산을 다 써서 빈 답변을 내놓는 문제, 이번 개발 과정에서 실측하고 고쳤다)는 이 조사에서 찾은 "추론모델
truncation" 이슈와 정확히 같은 유형이며, OpenAI 공식 문서와 여러 평가 프레임워크 이슈 트래커에도 알려진
실패 패턴이다.

**최소한 도입할 만한 평가 체계 제안**:
1. 골든 Q&A 세트를 만들어 배포 전 회귀 테스트로 돌리기
2. RAGAS/FActScore 방식의 faithfulness 자동 대조(답변이 실제 summary 수치와 일치하는지)
3. truncation/빈 응답에 대한 가드레일(이미 이번에 `CHAT_MAX_TOKENS` 상향 + 재시도로 1차 조치함)
4. SelfCheckGPT식 샘플링 기반 일관성 셀프체크

## 종합: 우리 프로젝트는 스펙트럼 어디에 있는가

다섯 분야를 관통하는 결론은 하나다 — **우리 시스템은 각 분야에서 가장 단순한 극단(구조화 질의 없음,
검색 없음, 도구 호출 없음, 시각화 없음, 자동 평가 없음)에 위치한 "정적 컨텍스트 주입형" 챗봇**이라는
것이다. 이는 과제 범위와 데이터 규모(120건)를 고려하면 합리적인 선택이지만, 데이터가 커지거나 요구사항이
복잡해질수록 위 5개 분야에서 제시한 방향(검색 도입, 도구 호출, 시각화, 자동 평가)으로 하나씩 확장해 갈
수 있는 명확한 로드맵이 존재한다는 뜻이기도 하다. 특히 과제의 보너스 항목(Function Calling, 시각화)은
정확히 이 로드맵의 3번·4번 항목과 일치한다.
